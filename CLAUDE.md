# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AcePlace is a tennis marketplace (university project, UI in pt-BR). The entire app is a single file, `index.html` (~1.6MB, ~1370 lines): no build step, no package manager, no tests, no linter, not a git repo. To run it, open `index.html` in a browser (or `python3 -m http.server` in this directory). Google Fonts is loaded from the network; everything else is inline.

## Reading and editing `index.html`

Three lines hold base64 image data (line numbers drift as the file grows; find them with `awk 'length($0) > 2000 { print NR }' index.html`) and are 50KB–1.4MB each. **Do not `Read` the whole file** (it exceeds the tool limit) and don't print those lines unfiltered. Use `Read` with `offset`/`limit`, or `sed -n 'A,Bp' index.html | cut -c1-200`.

- Line ~480: `PRODUCT_PHOTOS` (product id → array of `data:image/jpeg` URLs; 1.4MB). Since the Unsplash change these are only the **offline fallback**; deleting the whole var would just make the fallback the SVG art.
- Line ~658: `BRAND_LOGOS` (seller → PNG data URI)
- Line ~659: `HERO_PHOTO` (home hero image)

`Edit` needs unique `old_string` matches, so anchor on the surrounding short lines and never include these blobs in a match. When adding a product photo, edit the `PRODUCT_PHOTOS` line with a script (e.g. python) rather than by hand.

## Architecture

Everything lives in one IIFE inside a single `<script>`. It is a vanilla-JS hash-routed SPA that re-renders by string concatenation.

- **Data (top of script):** `PRODUCTS` (keyed by id; fields `seller`, `name`, `tag`, `price`, `shipping`, `description`, `specs`), `SELLERS`, and `SELLER_CATEGORY`/`SHOP_CATEGORIES`/`SHOP_CATEGORY_SLUGS`. The three sellers (StringLab, CourtWear, MatchStep) each map to exactly one shop category, so a new product's category is derived from its `seller`, not stored on the product.
- **Product photos:** `photoUrl()`/`galleryPhotos()` look in `LOCAL_PHOTOS` first, then `UNSPLASH`. `LOCAL_PHOTOS` lists, per product id, files from the project's `images/` folders (one subfolder per product, made by the user), in the order **product alone first, player (`*_lifestyle`) last**; every image was opened and classified by eye. The site does **not** load the originals in `images/` (30 PNGs of 3-8 MB, ~170 MB): it loads web-sized JPEG copies in `images-web/<slug>/<same-name>.jpg` (max 1600px, ~8 MB total, `LOCAL_DIR`). After adding or changing a photo in `images/`, regenerate its copy with `sips -Z 1600 -s format jpeg -s formatOptions 80 "images/<folder>/<file>.png" --out "images-web/<slug>/<file>.jpg"` and add it to `LOCAL_PHOTOS`. Folder → product: each `images/<name>` folder maps to the product with that name; three folders are not 1:1: `Corda e acessórios pequenos` (files are `natural_gut_130`) → Corda Natural Gut; `TENIS TENIS - UNISSEX` (2 shared images: `side`, `lifestyle`, both labelled "mens") → **both** Tênis MatchStep products; `shorts - fem e masc` → one image each (`mens_shorts_front` → Masculino, `womens_skort_front` → Feminino). Products with 1 photo (shorts) show no thumbnails. **The catalog is exactly the products that have a folder in `images/`** (13): the Raquete Premium had none and was removed. `UNSPLASH` (direct `images.unsplash.com/photo-…` URLs, no API key, optional focal-point crop `c`) is now empty and only a fallback path for a product added before its folder exists (only `images.unsplash.com/photo-…` is free, `plus.unsplash.com/premium_photo-…` is paid); if you use it again, restore the "Fotos: Unsplash" credit in `footer()`. To add a product: add it to `PRODUCTS`, make its `images/<name>/` folder, then add its web copies and a `LOCAL_PHOTOS` entry. If an image fails to load, the capture-phase `imageFallback()` listener (on `#app` and `#viewer`, because image errors don't bubble) swaps in the embedded `PRODUCT_PHOTOS[id][0]` (base64, offline fallback) and adds `.cutout`, which switches the CSS from full-bleed `object-fit: cover` to contained-on-a-light-panel. Without either, `productArt(id)` (inline SVG chosen by **id prefix**: `raquete*`, `corda-*`, `overgrip*`, `antivibrador*`, `camiseta*`, `shorts*`, `viseira*`, `tenis-*`, `meia*`) is the last fallback.
- **State:** one mutable `state` object (cart as `{key: qty}` where `key` is `productId` or, for products with sizes, `productId|size` (see Sizes below), wishlist, coupon, UI flags, account tab, privacy toggles). Nothing is persisted except product reviews, so a reload resets the cart to the seeded demo items. `COUPONS` maps code → discount fraction, and `COUPON_FREE_SHIPPING` marks which codes also waive shipping; the applied code is kept in `state.couponCode`. `TENIS10` = 10% off **and** free shipping. The site has no accounts or order history, so "primeira compra" is modelled by that coupon: the top promo banner (`promoBanner()`) advertises both 10% and free shipping, so keep its text, `COUPONS` and `COUPON_FREE_SHIPPING` consistent.
- **Routing:** `parseRoute()` reads `location.hash`: `#/`, `#/produtos[/<category-slug>]`, `#/produto/<id>`, `#/marca/<Seller>`, `#/carrinho`, `#/checkout`, `#/conta`, `#/cadastro`, `#/sobre/<slug>` (`proposito`, `quem-somos`, `sustentabilidade`; an unknown slug shows the home). `#/#<anchor>` is a home-page anchor scroll (handled at the end of `render()`), not a route. `hashchange` closes the menu, syncs `state.shopCategory` from the slug, and calls `render()`.
- **Rendering:** `render()` picks a `view*()` function that returns an HTML string, then sets `#app`.innerHTML to `header() + <main> + footer()`. The whole DOM is replaced on every render, so any transient DOM state (input focus, typed text) is lost unless it is stored in `state` (see `state.couponInput`). When the route (`parseRoute()` result, not the raw hash) changes, `render()` also scrolls to the top and turns on the scroll reveal (below); a re-render on the same route does neither.
- **Events:** a single delegated click listener on `#app` dispatches on `data-action="..."` (with `data-id`, `data-category`, `data-tab`, `data-key`, `data-index`). To add an interaction, emit a `data-action` in a view and add a branch in that `if/else if` chain. Most branches mutate `state` and call `render()`. `buy-now` and `go-checkout` rely on the link/hash change to render instead.
- **Footer, "Produtos mais buscados" and About pages:** `footer()` renders `mostSearched()` (the tabbed link section) followed by `<footer class="site">` with three columns: brand + tagline, "Ajuda" and "Sobre a AcePlace". Both are part of `footer()`, so they appear on **every** route. `HOT_TABS` is the data (tabs → columns → links); a link is `{ t, id }` (exact product → `#/produto/<id>`) or `{ t, cat }` (generic term → `#/produtos/<category slug>`); **only products that exist in `PRODUCTS` may be listed** (the Raquete Premium was removed from the catalog, so it is deliberately absent). "Cordas de tênis", "Overgrips" and "Antivibradores" point at the Raquetes & Cordas category because they are generic terms. All four panels are in the DOM and `selectHotTab()` toggles `hidden`/`aria-selected`/roving `tabindex` **imperatively** (no `render()`, so no scroll jump); arrows, Home and End work from the delegated `keydown` on `#app`; the chosen tab is `state.hotTab`. The "Ajuda" items (`HELP_ITEMS`) and "Trabalhe conosco" are deliberately static text, not links, because there are no support or careers pages. The copy of the three About pages lives in `ABOUT_PAGES` (paragraphs split on a blank line, rendered through `escapeHtml`); it was supplied by the user, with two garbled spots repaired minimally in `proposito` ("nasceu de uma constatação:") and `quem-somos` ("não pesa no treino e a aderência de um tênis").
- **Side menu and signup:** `menuPanel()` (opened by the hamburger, `state.menuOpen`) has an accordion: the "Todos os produtos" `<button aria-expanded>` shows `#menu-products-sub` with "Ver todos os produtos" plus the 3 real categories from `HOME_CATEGORIES`. The toggle is **imperative** (flips `.open`/`aria-expanded` directly, state in `state.menuProductsOpen`) on purpose: a `render()` would replace the DOM and skip the `grid-template-rows: 0fr → 1fr` animation; collapsed links get `visibility:hidden` so they are not tabbable. Any click on a `.menu-panel a` closes the menu (and re-renders when the link points at the current hash, since no `hashchange` fires then); the accordion always reopens collapsed. "Cadastre-se" is in the top `nav.main` (hidden below 720px) and, for that reason, also in the menu's Conta section. `#/cadastro` (`viewSignup()`) validates in `validateSignup()` from a delegated `submit` listener, showing errors by writing to `#err-<field>` directly (no re-render, so typed text and focus survive). There is no backend: on success it only sets `state.signedUp` (name/email, in memory, cleared on the next route change), the password is never kept anywhere, and the success text says it is a demo.
- **Checkout:** "Finalizar pedido" is a plain link to `STRIPE_PAYMENT_LINK` (a Stripe **test-mode** payment link). Its click handler only runs the HTML5 form validation of `#checkout-form`. There is no backend, and the Stripe link does not reflect the cart contents or the coupon.
- **Sizes:** `sizeOptions(p)` decides which products have a size selector, by id prefix: `camiseta*`/`shorts*` → P, M, G, GG (fixed, even though the feminine specs text says "PP ao G"); `tenis-*` → the range parsed from the spec line `Numeração: 38 a 44` (so editing the spec changes the buttons); everything else (racquets, string, overgrip, dampener, visor, socks) has none. `sizeSelector()` renders between the specs card and the quantity row. The choice lives in `state.sizeSel[productId]` (nothing preselected; reset after adding to the cart and on route change; kept across same-page re-renders). "Adicionar ao carrinho" and "Comprar agora" share one branch of the click handler: without a size it sets `state.sizeError`, focuses the buttons and `preventDefault()`s (which is what stops the buy-now link from navigating). **Cart keys carry the size**: use `cartKey(id, size)` / `splitKey(key)` and never `PRODUCTS[key]` on a cart key; `cartItemRow()` and the checkout summary print `(Tamanho X)`. The same product in two sizes is two lines; the same size merges. `data-id` on cart-inc/dec/remove is the key, so tests must select with `[data-id^="product-id"]`.
- **Checkout shipping and benefits:** checkout shipping is a flat `SHIPPING_FLAT` (R$ 19,90) unless `freeShippingApplied()` (coupon with free shipping); the per-product `shipping` values are only shown on product pages. `benefitBanner()` renders above the order summary (inside `.checkout-side`) on **both the cart (`viewCart()`) and the checkout**, as does `checkoutCouponField()`; the cart and checkout summaries share one column layout, so change them together from `BENEFIT_TIERS` (R$ 350 → Viseira Court Basic de brinde, R$ 500 → aula experimental de tênis). The amount compared is the **product subtotal, before coupon and shipping**, thresholds are inclusive, and `benefitState()` works in cents to avoid float errors (e.g. 349,90 is 10 cents short). It shows the next tier as an incentive, both as conquered above the top tier, and a generic explanation for an empty cart. The gift and the class are only announced: they are not added to the cart, the summary or the Stripe link. The coupon field (`checkoutCouponField()`, despite the name also used in the cart, id `cupom-checkout`, action `apply-coupon-checkout`, inside the summary card so it is outside `#checkout-form`): it applies `COUPONS` codes (any case, trimmed) into the same `state.coupon`/`state.couponCode` as the product page, an invalid or empty code only sets `state.checkoutCouponError` and never removes an already applied coupon or blocks "Finalizar pedido", Enter in the field clicks Apply, and both `checkoutCouponInput`/`checkoutCouponError` reset on route change. The success line is derived from `state.couponCode` (not from `couponMessage`), so it is always accurate when you arrive from the product page. To unit-test `benefitState()`/`benefitBanner()` at exact boundaries (real carts cannot hit R$ 350,00 or 500,00 because every price ends in ,90), inject `window.__t = {...}` into the extracted script in the test only.
- **Styling:** one `<style>` block using CSS variables, with light defaults on `:root` and dark overrides under both `prefers-color-scheme` and `:root[data-theme="dark"]`. Fonts are Archivo (headings) and Work Sans (body).
- **Motion:** elements with `.reveal` (optionally `style="--i:N"` for stagger) fade/slide in via an `IntersectionObserver` set up in `setupReveal()`. The hidden state only exists under `.animate` on `#app`, which `render()` sets only on a route change, so add-to-cart and other same-route re-renders never replay it. Everything respects `prefers-reduced-motion`.
- **Home / photo tiles:** `viewHome()` is built from `productTile()` (full-bleed photo above a light `--tile` caption panel; hover zooms the photo), `categoryPanel()` (photo with a dark gradient and white text) and `sellerBand()` (alternating brand bands with a 3-photo collage). The featured product and category fallbacks are constants (`HOME_FEATURED`, `HOME_CATEGORIES`). The `--tile*` tokens are deliberately **not** overridden for the dark theme. `AMBIENT_PHOTOS` (category label → up to 3 lifestyle photos as data URIs: `[0]` category panel, `[1]` brand band, `[2]` reserved for shop/brand banners) is still empty and optional: the home now uses the Unsplash product photos for those slots.
- **Photo viewer:** clicking the main photo on a product page calls `viewerOpen()`, a fullscreen overlay that lives in `#viewer`, *outside* `#app`, because `render()` would wipe its zoom state. It is imperative code with its own state (`vw`): wheel/pinch zoom, drag to pan, swipe and arrow keys between photos (when there are several, e.g. the offline fallback), double-tap to zoom. Zoom is capped by photo resolution (`viewerMaxScale`). It closes on Esc, the close button and `hashchange`, and it traps focus.
- **No 360°:** a realistic 360° is not possible from a single photo (it distorts), so the interaction is the tilt below instead. An earlier version had procedural 3D turntable models on a canvas; they were removed when the photos moved to Unsplash, since a generic 3D model no longer matched the photo.
- **Tilt + dynamic shadow:** the main product photo (`.tilt`) turns towards the mouse by up to `TILT_MAX` = ±18° (`perspective(1700px)`, larger perspective keeps the near edge from overflowing the page) and shows a moving glare. A blurred `.tilt-shadow` under it moves opposite to the cursor and gets larger/stronger with the tilt (`--sx/--sy/--sb/--so` on `.photo-stage`). It is set imperatively via CSS variables by a delegated `pointermove` on `#app` (mouse only, disabled under `prefers-reduced-motion`), so it never goes through `render()`. The shadow is only visible on the light theme; on the dark page it is nearly invisible.

## Gotchas

- Views build HTML by string concatenation and only escape where they call `escapeHtml()`. This is fine for the static `PRODUCTS` data, but always wrap user-typed input (as the review form does) before interpolating it.
- **Reviews:** `state.reviews` (`{productId: [{rating, name, comment, date}]}`) is the only persisted state, in `localStorage` under `aceplace.reviews` (reads and writes are wrapped in try/catch). `viewReviews()` renders below the product grid. The form's typed text lives in `state.reviewDraft`, synced by a delegated `input` listener (`data-review-field`), so it survives `render()`. There is no seed data, so products start with no reviews.
- The account "Pedidos" tab uses a hardcoded `orders` array inside `accountPedidos()`, and the password/privacy forms only flip flags in `state` (no real auth or storage).
- **Removed products:** `viewProduct()` shows the full catalog (resetting the shop filter to `Todos`) for any product id that does not exist, so old links such as `#/produto/raquete-premium` land on the catalog instead of erroring. Reviews saved in `localStorage` for a removed product are simply ignored. The home `HOME_CATEGORIES[].fallback` product ids must exist in `PRODUCTS`.
- **Photos:** photos have mixed aspect ratios and are shown with `object-fit: cover` (cropped). The 2:3 portrait shots (`raquete-*_front`, `camiseta-*_front`) get cropped into wide frames, so two CSS rules near the end of the `<style>` (`img[src*="/raquete-"][src$="_front.jpg"]`, same for camiseta) keep the racquet head / shirt collar in view; the viewer (`contain`) and the thumbnails show the whole product. Unsplash URLs (currently unused) take a `w=` width param, never below 1200. The photos come with visible third-party brands (e.g. Adidas, Head, Yonex): that is inherent to stock photos. The embedded fallback photos are at most 640px wide, one of them (`raquete-tour-100`'s second) has a fake transparency checkerboard baked in, and the men's t-shirt one has a watermark.

## Verifying changes

There is no Node. Logic can be tested by extracting the `<script>` body and running it with stubbed `window`/`document` in `jsc` (`/System/Library/Frameworks/JavaScriptCore.framework/Versions/A/Helpers/jsc`, which has `print` and `read`). Layout can be checked with headless Chrome: `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --screenshot=out.png --window-size=1440,4700 --virtual-time-budget=6000 file://.../index.html`. Use a window tall enough for everything to intersect, since headless doesn't fire the `IntersectionObserver` after a scroll. Interactions (viewer, tilt) can be tested by embedding the app in a same-origin `<iframe>` (`--allow-file-access-from-files`) and dispatching `PointerEvent`/`WheelEvent`/`KeyboardEvent` into `iframe.contentDocument`. Headless Chrome has network access, so Unsplash photos really load; with `--virtual-time-budget` **CSS transitions do not advance** (a panel measured right after a click still reads its old height), so for layout assertions inject `*{transition:none !important}` into the iframe, and to prove an animation exists use the Web Animations API (`el.getAnimations()`, then `.finish()`). Changing only the `#hash` of an iframe's `src` does not reload it, so `load` never fires: add a throwaway query string (`?n=1`) when you need a fresh page. In jsc stubs, `closest(sel)` must answer only the selector it should match, because the click handler now asks for `.menu-panel a` before `[data-action]`; to check all photo URLs, `curl -o /dev/null -w '%{http_code}'` each one. Don't trust an HTTP 200 alone for a *new* photo: render it (e.g. a contact sheet page screenshotted in headless Chrome) and look at it. For real mobile widths, embed the page in a 420px-wide `<iframe>` inside a wrapper page, because headless Chrome enforces a minimum window width.
